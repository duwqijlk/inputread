# 阅读器词典功能 v1：已确认规则与维护权限（讨论记录第 2 版）

记录日期：2026-11-07。
状态：需求讨论记录，未实施；不是代码、数据库或线上数据修改授权。
本文件取代 `../v1/DICTIONARY_MAPPING_AND_COMMUNITY_MEANINGS.zh-CN.md` 中与之冲突或仍标为待定的规则；旧文件保留为讨论历史。这里 v1 指计划开发的功能版本，v2 目录指本记录的第二版。

## 1. 最重要的权限边界

**标准词典有专门的维护者和维护流程，不由本阅读器会话，也不由夜间巡检 agent 维护。**

| 角色/系统 | 允许 | 禁止 |
| --- | --- | --- |
| 独立标准词典维护流程 | 按其独立授权维护标准解释、发布可供读取的词典版本 | 本文不给该流程新增任何权限；新增/变更 ID 的政策不在阅读器 v1 内决定 |
| 阅读器查询 API | 读取已发布标准词典、按词形或既有 sense ID 返回释义 | 创建 sense ID；改写词典标准释义；把用户原稿写成词典标准 |
| 夜间巡检 agent | 从标准词典选择已有义项，维护书内位置映射，审核维护一条社区解释，处理位置报错 | 新建、删除、合并、替换或编造标准义项 ID；编辑标准词典正文；发布新标准词典构建 |
| 用户 | 对未固定位置选择一个候选义项，改票/取消；Write my own；报告错误 | 直接固定标准映射；直接覆盖公开社区解释或标准词典 |

权限应由实际凭据、路由和写入白名单保证，不能只在提示词里约定。面向阅读器的词典资源为只读；夜间巡检不持有可写标准词典仓库/正文的权限。位置映射 ID 必须存在于已发布词典，并验证其词条、词性和语境适用性，不接受任意字符串冒充 sense ID。

**本项目不允许创造新的释义 ID。** 找不到合适的已有义项时，保留社区解释，不硬绑、不自行造 ID。最多报告“标准词典暂无匹配”及相关证据给独立维护者；报告不是自动开工、修改或跨会话授权。

## 2. 固定义项身份与解释文字修订

- 一个 sense ID 对应一个固定意思。
- 独立词典维护者可以把同一意思解释得更简单、自然，ID 不变。
- 解释文字修订号/构建号只用于资源追踪和缓存，不是新的义项身份。
- 阅读器 API 下次实际获取新数据时返回更新后的解释，不提示读者手动升级。
- 解释改写不会清空位置投票，不需要重新标注同一 ID 的书内位置。
- 只有独立维护流程明确发布的特殊兼容变更，才另行讨论迁移；阅读器和巡检不得猜测、执行未经授权的 ID 替换。

## 3. 三个层面必须分开

1. **标准词典**：固定 sense ID 及其标准学习释义，全站共享，只读使用。
2. **书内位置状态**：该准确位置未固定/已固定到哪个既有 sense ID，以及未固定时的投票。
3. **社区解释**：该位置最多一条经夜间 agent 审核认可的英文解释，与标准区并列，不属于标准词典正文。

旧词表已经写好的解释按兼容规则保留并归入旧内容/社区解释层，保留来源与贡献署名；不能改个标签便宣称它来自标准词典。旧数据的准确位置恢复和发布迁移方式仍需设计，不能无证据把一条广泛适用旧词条复制成每个位置的社区解释。

## 4. 词卡展示已确认规则

### 4.1 已固定标准映射的位置

- 默认只返回已固定 sense ID 的标准解释，不返回整个单词全部候选。
- 不再展示义项投票入口，也不允许后台继续计票。
- 有社区解释时，**标准在前、社区在后，两条都默认展开**。
- 社区解释最多一条；没有社区解释不放空白占位。
- 保留“意思不对”反馈，由巡检核对后修正/撤回位置映射，不按新的票数竞争自动换义项。
- 不因修改标准解释文字而解除位置固定状态。

### 4.2 尚未固定标准映射的位置

- 返回该单词/匹配词条的全部候选标准义项。
- 只按**当前位置**的有效票数排序；没有票时按确定的词典默认顺序。
- 有一条审核通过的社区解释时仍独立显示，不能冒充已确定标准义项。
- 巡检处理社区解释时同时尝试选择已有标准义项；有可靠对应则固定，没有则保留社区解释并明确无标准匹配。
- 未收录或查询失败不能伪造解释，也不能将网络失败长期缓存为“未收录”。

### 4.3 两条解释不能相互矛盾

社区解释应当适用于同一位置的原句。若它表达的是另一义项，首先作为**标准映射可能错误**处理，核对并修正映射后再决定是否展示社区解释；不直接把互相冲突的意思并排当成正确答案。

所有阅读内容解释保持英文，简单、准确、自然；中文用于界面与维护文档。所有词可点击不等于所有词画线，继续保留难词突出和短语等既有阅读边界。

## 5. 位置身份与投票规则

逻辑作用域：

```text
公共书籍身份（例如 catalog + id）
+ 文本/坐标版本
+ 精确位置锚点
```

标准义项投票目标在该位置上再加 sense ID；用户去重加用户身份。相同单词在同书不同位置、不同书或无法可靠对应的文本版本间，不共享票数或排序。

已确认：

- **只有已登录且邮箱已验证的用户可以投票**，服务端做鉴权，不仅前端隐藏按钮。
- 每位用户每个位置只支持一个标准义项，可改选、可取消；不能按每个 sense 分别各计一票绕过单选。
- 候选必须属于该位置当前返回的合法标准候选集合。
- 夜间复核初始门槛：领先义项至少获 **5 位不同有效用户**支持，且占该位置当前有效票数 **70% 及以上**。
- 此门槛仅触发复核，不直接自动固定；同一位置的分母是当前有效选择数，不是点击次数，也不是全词/全书票数。
- 达到门槛后，agent 核对原文坐标和语义，确认再发布直接映射。
- 固定后退出投票流程。后端必须拒绝过期页面提交的新票；不能只从界面移除按钮。
- 改票、取消、重试、并发及巡检重复执行不能重复计数；固定操作须重新验证位置仍未固定和复核基线未失效。

“5 人、70%”是用户选定的 v1 初始规则，不代表已经由真实使用数据证明最优；后续调整需要明确记录，不悄悄改变。

## 6. 夜间巡检的两条职责

### 6.1 未固定位置 → 确定标准映射

```text
合法候选与位置投票
→ 5 位用户且领先支持率 ≥70%
→ agent 复核原句、锚点、已有 sense ID
→ 更新书内映射数据/JSON
→ 此位置改为直接引用该 sense ID
→ API只返回该标准义项，投票关闭
```

固定的是引用关系，不是标准解释文字快照。巡检不编辑标准词典。

### 6.2 Write my own → 维护一条社区解释

沿用现有夜间巡检处理用户建议的方式，不建立提交后立即公开的评论流。

- agent 认可解释适用于这个位置后，作为该位置唯一公开社区解释固定下来。
- 同时尝试选择合适的既有标准义项；不存在适合义项则保持“无标准匹配”。
- 新建议只有更准确或更容易理解时才替换现有社区解释；仅仅同样正确不构成替换理由。
- 替换后仍只公开一条，保留历史、来源和实际采纳署名；不凭提交/点赞就授予采纳贡献。
- 用户补充不因为审核通过自动变成标准词典释义；同样不自动触发标准词典修改。
- 本人待审稿即时显示与否沿用现有提交体验，是否另加本地草稿视图未决定，不误写成已批准功能。

### 6.3 已固定位置的报错

已固定映射可以通过“意思不对”反馈进入夜间巡检。agent核实后可修正到另一个**已有合法 ID**，或撤回错误绑定。撤回后的候选/重新投票具体处理仍需明确，不能自动恢复历史票数并立即反复固化。

## 7. API 职责与缓存

具体技术栈、数据库、路由与最终 Schema 尚未确定。

需要的读能力：

- 按已知 sense ID 解析标准解释，支持批量读取。
- 按词形查询全部合法候选义项，处理词形还原和歧义。
- 按准确位置读取未固定/固定状态、唯一社区解释、未固定时的票数。
- 聚合返回时仍明确区分标准数据、位置数据、本人私有状态。

需要的写能力：

- 仅已验证用户可对未固定位置单选投票、改票、取消。
- Write my own 和错误反馈按现有鉴权/提交维护流程演进。
- 受限巡检发布位置映射和社区解释；没有标准词典写接口。

缓存已确认：

- 标准解释允许**正常最多约1小时**缓存延迟，不提示用户手动更新。
- 要考虑浏览器、服务端/CDN、进程内缓存叠加，不能每一层各缓存1小时导致实际超过约定。
- 相同词典义项可共享公共缓存；位置票数和社区解释必须以准确位置区分。
- 固定状态切换与个人投票状态不能直接套用标准解释的1小时公共缓存，具体一致性策略另定。
- 服务端以真实固定状态拒绝过期投票，即使客户端仍显示旧候选。
- API每次展开是否实际发网络请求、短期缓存怎样复用仍需技术设计，不把“下次请求得到新值”误写为“所有点击一定打数据库”。

## 8. 新旧词表与联网范围

- 保留旧释义、短语、贡献、进度和学习数据，不强制重做旧词表。
- 新书使用准确位置到已有 sense ID 的映射；旧书可增加位置映射补充层。
- 同一本书允许旧内容、新映射、未映射位置共存。
- v1 **不要求未缓存普通词在离线状态可查询**，优先围绕联网API设计；这是一项产品范围选择，不代表现有网站的所有离线能力不存在。
- 是否预取书内已映射释义、怎样保存收藏时的解释快照、API故障回退仍待确定。
- 不为标准释义更新重新占用下载名额或将书籍标记为新上架。

## 9. 安全、成本与验证原则

- 位置投票、映射和社区解释与标准词典分别存储/授权；标准源只读。
- 服务端验证会话、邮箱状态、位置身份、候选ID、固定状态和单选唯一性。
- 防止输入注入、恶意内容和刷票；社区解释作为纯文本处理，保留现有长度与内容安全约束。
- 不为每次普通点击都新增 D1 写入或夜间工作项。
- 数据库大小、索引写放大、投票吞吐、缓存命中、构建/导入成本要实测，不能仅由词条数判断免费额度是否足够。
- API和数据库尚未选择，D1、R2分块或其他方案需基于已确认规则比较，本文不预先定死。
- 新词典资源采用明确来源与构建标识。标准ID必须从已发布资源中验证，不以字符串格式正确代替存在性验证。
- 位置验证检查源文本、Unicode码点偏移、所见词形、词条/义项绑定和坐标版本；不要逐卡模拟点击代替字典坐标校验。
- 沿用巡检有界分页、截止/基线、实际审核ID、备份、发布回读、贡献核验和失败不完成等安全要求。

## 10. 尚待选择的问题

1. 具体数据库/缓存/部署架构，以及实际SQL服务库的大小、行数和索引。
2. 公共位置身份、文本版本、锚点规范与不同版次对齐。
3. 固定映射撤回后如何处理旧票；哪些票计为当前有效，账号删除/邮箱状态变化如何处理。
4. API故障或已有映射ID暂时无法解析时怎样显示，是否保留已缓存解释。
5. 收藏/生词本保留当时解释还是跟随标准释义更新；社区解释更新是否同步影响收藏。
6. 未固定时全部标准候选与唯一社区解释的具体卡片布局；大量候选的分页/折叠。
7. 标准词典没有匹配时，后续怎样接收独立维护者的新资源通知；阅读器不能自行补造ID。
8. 并列展示的两个解释几乎相同时是否仍两区展示，不能在未决定前擅自合并来源。
9. 唯一社区解释替换历史、署名和原有反馈/贡献记录如何兼容。
10. 未固定位置的候选、固定状态与个人投票状态的短期缓存一致性。

## 11. 实施边界

本轮只记录已讨论规则。正式开发前需单独制定协议、表结构、权限、迁移和测试方案，并更新现行巡检工作文档；本文不直接更改 `docs/GLOSSARY_PATROL.md` 的权限或 SQL。

任何将“巡检维护社区解释”解释为“巡检可以维护标准词典、创建 sense ID”的实现，都不符合本记录。
