# 阅读器词典功能 v1：开发准备说明

讨论记录第 3 版 · 2026-11-07

**状态：已确认的产品规则与开发边界，尚未实施。** 数据库、API 技术栈、Schema、迁移与发布方案仍需设计；本文不构成代码开发、标准词典维护或生产写入授权。

## 0. 阅读顺序与规则优先级

本文件整合本轮讨论，是当前开发准备入口。此前文档保留为历史：

- [讨论记录第 1 版](../v1/DICTIONARY_MAPPING_AND_COMMUNITY_MEANINGS.zh-CN.md)
- [讨论记录第 2 版](../v2/DICTIONARY_V1_CONFIRMED_RULES.zh-CN.md)

发生冲突时以本文为准。**功能 v1** 是计划开发的产品版本；目录 v3 是讨论记录版本，不表示功能已经发布三版。

本轮最重要的简化：

1. 标准词典只读，阅读器及夜间巡检不能创造释义 ID。
2. 点赞只用于未固定位置的候选排序和达到门槛后固定映射。
3. **收藏与点赞独立，取消二者的复杂联动。**
4. 每个位置只公开一条社区解释；旧内容保留，来源标签清晰。
5. 标准义项负责主要复习，社区/旧解释可独立收藏或作为辅助；原句按需限量读取。

## 1. 产品目标

- 兼容老词表内嵌解释和后续基于标准 sense ID 的位置映射，不强制重做老书。
- 所有单词都可点击；无书内确定映射时查询标准词典全部合法候选，不代表所有单词都画线。
- 有确定映射时只显示对应标准义项，不继续展示整词候选和投票。
- 同一位置可同时显示标准解释与一条社区解释，标准在前，两区默认展开。
- Write my own 沿用现有夜间巡检处理建议的维护方式，不改成即时公开评论流。
- 让位置点赞沉淀为直接映射，但不扩大标准词典维护权限，也不让投票操作控制用户收藏。

## 2. 标准词典权限与 ID 语义

标准源仓库：https://github.com/duwqijlk/english-wordnet

### 2.1 谁维护什么

| 角色 | 可以做 | 不可以做 |
| --- | --- | --- |
| 独立标准词典维护者/流程 | 按其自身授权维护标准学习释义、发布资源 | 本文不扩大其权限，也不替其制定新 ID 政策 |
| 阅读器后端/API | 读取已发布标准词典，解析既有 sense ID，返回解释 | 改标准释义，创建/编造/删除/合并标准 ID |
| 夜间巡检 agent | 维护书中位置到既有 ID 的映射；审核一条社区解释；处理位置反馈 | 编辑标准词典正文、创造义项 ID、代替独立维护者发布词典 |
| 用户 | 对未固定位置点赞；收藏已有解释；Write my own；报错 | 直接发布标准映射或覆盖公开解释 |

权限须落实到凭据和接口白名单，不能只靠 agent 提示词。巡检不得拥有可写标准词典源的权限。

### 2.2 固定 ID 与解释改写

- 一个 sense ID 代表一个固定意思。
- 独立词典维护者把同一意思解释得更简单，ID 不变。
- 解释修订/构建标识用于缓存和追踪，不是新义项身份。
- 读者下一次实际请求取得更新解释，不提示手动升级。
- 标准解释文字改变，不使位置映射失效，也不清空相关历史投票。
- 找不到合适已有义项时，保留社区解释，明确标准无匹配；不硬绑、不造 ID。
- 可以记录缺项证据供独立维护者参考，但记录不等于授权任何本项目 agent 修改标准词典。

## 3. 数据层分离

至少明确区分：

1. **标准词典资源**：词条、词形、词性、固定 sense ID、标准学习释义、来源/修订，只读使用。
2. **位置映射**：准确书中位置是否已经固定，以及固定到哪个已有 sense ID。
3. **位置投票**：未固定位置上各标准候选的有效支持，不属于词典正文。
4. **社区/旧解释**：当前位置可用的非标准解释、来源、署名和审核记录。
5. **个人收藏与复习**：用户收藏的标准义项或社区辅助项、原句来源及学习状态。

不得把位置票数写进公共义项缓存，不得把用户补充审核通过误当成标准词典采纳。

## 4. 位置身份：绝不跨位置串数据

逻辑位置身份：

```text
公共书籍身份（例如 catalog + id）
+ 文本/坐标版本
+ 精确锚点
```

- 不能用设备本地随机 bookId、书名、单词拼写或章节单独代表公共位置。
- 同书 bank 第一次和第三次出现，投票、社区解释和映射均各自独立。
- 不同书、无法证明对应的 EPUB 版次不共享位置数据。
- 词典解释修订与文本坐标版本分开，不能因解释改写失去锚点。
- 精确检查原文、Unicode 码点偏移、所见词形、源文本成员关系和 sense 绑定。
- 字典生成验证以本地坐标/结构检查为主，不逐卡模拟点击代替坐标核验；实际阅读器 UI 开发另做浏览器交互验证。

## 5. 词卡的状态与返回内容

### 5.1 未固定标准义项

- 标准区返回所点词形匹配到的全部合法候选义项。
- 按当前位置的票数排序；没有票时采用确定的标准默认顺序。
- 允许符合鉴权条件的用户点赞，票数不跨位置复用。
- 已有社区解释可单独显示，不冒充已固定标准意思。
- 查询失败与词典未收录必须区分，不能伪造结果。

### 5.2 已固定标准义项

- API只返回该位置已固定的 sense ID 对应解释，不返回全部候选。
- 关闭投票入口，服务端也不再接受该位置新票。
- 有社区解释时：**标准在前、社区在后，默认同时展开**；每位置最多一条社区解释。
- 标准映射固定后不随实时热度反复变化。
- 保留“意思不对”反馈，巡检可纠正到已有合法 ID；不把撤回、重投、重新固化设计成 v1 常规交互。
- 固定状态下更正错绑仍是位置维护，不是编辑标准义项内容。

### 5.3 只有社区/旧解释

- 有可用解释就显示，不为凑双区再生成一段标准解释。
- 允许收藏，不要求先补标准 ID 或投票。
- 后续获得确定标准映射后，可转为标准卡，原社区解释作为辅助保留。
- 标准与社区都没有内容时，不建立没有解释的收藏。

## 6. 社区解释与旧版解释来源

每个准确位置最多公开显示一条社区解释，不能变成多条回答列表。

| 内容来源 | 展示规则 |
| --- | --- |
| 老词表中 agent 生成、没有用户署名的解释 | 标为“旧版解释”，不虚构作者或 From 署名 |
| 老词表中已有用户贡献署名的解释 | 保留原有 From … 和贡献身份 |
| 新 Write my own 通过审核的解释 | 作为该位置社区解释，保留实际作者 |

旧内容属于社区/旧内容兼容层，不来自标准词典。原有词表适用位置、短语、段落帮助、贡献信息和阅读数据要保留；不能无证据把一条旧词条扩散为所有位置的专门解释。

### 6.1 Write my own 的维护

- 用户提交仍由夜间 agent 检查原句、位置与英文解释，沿用既有建议维护方式。
- 正确适用后固定为该位置唯一社区解释，不立即公开未经审核稿。
- 处理社区解释时同时尝试选择已有标准义项；无合适义项就仅保留社区解释。
- 新稿必须更准确或更易懂，才替换已有社区解释；仅“也正确”不足以反复换稿。
- 当前解释署新稿实际作者，旧稿、旧作者及曾被采纳贡献保留历史，不被抹掉。
- 社区解释与固定标准意思冲突时，先按映射错误核对，不把两个相互矛盾的意思并列当成正确答案。
- 不因社区解释通过审核而改标准词典，也不新增 sense ID。

## 7. 点赞：仅用于位置固定

### 7.1 已确认规则

- 仅**登录且邮箱已验证**用户可投票，服务端鉴权。
- 每位用户每个位置只能支持一个标准义项，可改选、可取消；重复点击不累加。
- 目标必须是当前词条合法的已有候选 ID。
- 初始固定条件：领先义项至少获**5 位不同有效用户**支持，且占当前位置当前有效票数**70%及以上**。
- 夜间流程检索达到条件的位置，写入直接映射；不另设用户确认步骤，不再把“额外人工审批/逐项二次语义复核”作为票数固化的前置门槛。
- 夜间发布仍必须校验合法 ID、锚点、单选去重、截止/最新基线、位置仍未固定及发布结果。数据校验不等于获得标准词典写权限。
- 固定后不再返回全词候选，也不再开放投票。
- 用户提交旧页面上的过期票时，后端不计票，前端刷新到固定解释，不误报操作成功。

“5人、70%”是选定初始规则，后续改动要记录，不能悄悄变化。所有位置独立，不能把别处票数移入补足门槛。

### 7.2 本轮明确取消的复杂联动

以下旧讨论不再作为开发要求：

- 先点赞成功才能收藏；
- 改票就自动把收藏 A 换成 B；
- 取消点赞就删除收藏；
- 公共位置投票变化直接控制个人收藏和复习状态。

**点赞管公共位置映射，收藏管个人学习，两者独立。** 无投票资格或投票网络失败不应因本方案新增限制而阻止收藏已有解释；收藏接口本身仍遵守现有登录与权限要求。

## 8. 收藏和复习

### 8.1 收藏条件

- 有标准释义：可以收藏，以对应标准义项为主要学习内容。
- 只有社区解释或旧版解释：也可按原有行为收藏，明确实际来源，不编造标准 ID。
- 两者都没有：不能建立无解释的收藏。
- 未固定位置如何在多个候选中选择具体收藏目标，仍需在卡片/API设计时明确；不能恢复“强制先投票”，也不能静默收藏全部候选。

### 8.2 标准义项学习状态

- 同词归组、不同义项分别复习。
- 同词条、同 sense ID 的重复收藏归入同一学习项，关联多个准确原句来源，不重复建卡。
- 词形变化如 banks/bank 可依词条归一规则合并；不同同义词不因同 synset 或意思接近自动共享掌握度。
- 标准释义以映射/API提供的解释为主，随标准解释刷新，不默认锁死收藏时文字快照。
- 社区解释可作为复习辅助，但不替代有标准映射时的主要内容。

### 8.3 多位置来源按需读取

```text
某用户 · 同词条 + 同 sense ID
├─ 书 A · 位置 1 的收藏原句
├─ 书 A · 位置 20 的收藏原句
└─ 书 B · 位置 8 的收藏原句
```

- 在哪里收藏，就关联哪里的准确原句，不能把其他位置当成本句证据。
- 同一学习项可以有很多位置，但默认只展示部分原句。
- API/SQL必须限制实际读取与返回数量，不是先读几百句再只在前端隐藏。
- 具体默认几句、排序和是否按需翻页尚未确定，不预设3句或其他硬阈值。
- 原句分页不能导致重复收藏或复习状态重复创建。

### 8.4 社区辅助项与老卡兼容

- 没有标准义项的辅助项继续保留原句与社区/旧解释，能按原有方式使用。
- 后续该位置有确定标准映射时，转换为标准义项卡，社区解释作辅助；有同词条同 ID 学习项时合并相应来源。
- 老卡没有 sense ID 不强制重选或重新投票。只有能凭原句/位置可靠匹配时才迁移，不能按解释文字相似或默认第一义项硬绑。
- 其他既有复习状态和用户数据不可丢失；社区项转标准项时如何处理既有进度仍需明确。
- 本轮取消“投票操作自动改收藏”后，公共映射最终不同于用户原收藏义项时，不能暗中重新启用旧A→B联动；具体历史收藏纠正策略保留为技术/产品待定项。

## 9. 夜间巡检职责与文档升级

夜间流程承担两个清晰通道：

1. **标准位置固定**：达到有效票门槛 → 校验位置/合法 ID/最新基线 → 发布直接映射 → 停止该位置投票。
2. **社区维护**：审核 Write my own → 维护唯一适用社区解释及署名 → 尝试绑定已有标准义项或记录无匹配。

社区稿的内容审核仍保留；不能把标准票数固化的规则与社区稿审核混成一个流程，也不能因此允许新建标准义项。

正式实施需更新 `docs/GLOSSARY_PATROL.md`，并核对 `docs/MAINTENANCE.md`、反馈接口、贡献统计与署名规则。本文不直接扩大现行巡检权限或改SQL。

继续保留有界分页、截止时间、实际处理 ID、最新基线、备份与回读、失败不标完成的安全要求；只处理新增/变化候选，不每夜全表扫描。映射数据JSON、D1状态与缓存的发布不是天然原子事务，需要设计一致性与恢复。

## 10. API 职责与缓存

具体 URL、服务端框架、D1/R2或其他存储尚未确定。

需要的能力：

- 按已有 sense ID 返回标准解释，支持批量解析；
- 按词形返回全部合法标准候选；
- 按准确位置读取固定状态、唯一社区/旧解释、未固定时票数；
- 独立提交投票、Write my own、错误反馈和收藏，不把一个操作的失败误报另一个操作成功；
- 生词学习项及原句来源限量查询；
- 夜间流程受限写位置映射和社区解释，无标准词典写接口。

缓存规则：

- 标准解释正常更新延迟**最多约1小时**，不提示用户手动升级。
- 多层缓存要合计控制新鲜度，不能每层再续1小时。
- 标准API故障时可暂用之前成功取得的有效缓存并重试，故障期间可超过正常新鲜度；恢复后刷新，不把旧缓存当新发布数据。
- 位置状态/票数/社区解释以位置隔离；个人投票和私有提交不能进入公共缓存。
- 固定状态不能机械套用标准文字1小时缓存，后端必须拒绝固定后的过期投票。
- 词典不含该义项与临时超时要分开处理，不能用其他意思静默顶替。
- v1围绕联网API设计，不把全词典离线可查列为要求；不因此删除现有可用缓存和阅读能力。

## 11. 成本与安全

- 原句“只显示部分”必须落到数据库查询、API响应及同步策略，避免无限列表带来免费D1读取浪费。
- 不为每次展开卡片新增D1写入；投票/取消/提交按实际操作写入，评估索引写放大。
- 标准资源只读，用户数据与其版本发布分开。
- 服务端核验会话、邮箱验证、公共书籍身份、文本坐标、候选ID、位置状态及用户唯一票。
- 标准解释与社区稿是纯文本/受控内容，限制长度并防注入，不直接信任客户端上传的票数、ID或署名。
- D1容量、派生SQLite行数/索引体积、API请求、缓存命中和批量更新成本仍需测算，尚未决定“全部点词在线查D1”。

## 12. 已排除与尚待决定

### 已排除

- 阅读器或夜间agent维护标准词典、创造sense ID。
- 全局单词义项热度跨书/跨位置影响排序。
- 一个位置多条公开社区回答。
- 点赞作为收藏的强制前提或直接控制收藏增删/换义项。
- 固定后继续投票竞争、实时热度反复切换。
- 为简化数据而把所有旧解释冒充标准词典释义。
- 生词复习一次加载一个义项下所有原句。

### 尚待决定

1. 数据库/API部署方案及实际资源规模。
2. 位置坐标、版本、不同EPUB版次的可靠对齐协议。
3. 未固定时多个标准候选的具体收藏选择交互，但不以投票为前提。
4. 无标准映射的旧/社区收藏如何去重与复习；转标准时进度如何保留。
5. 公共映射最终与用户此前收藏义项不一致的纠正策略，不重新引入投票直接联动。
6. 原句默认返回数量、顺序、分页和跨设备同步上限。
7. 社区解释替换后辅助文字是否跟随更新，以及历史贡献计数方式；当前新作者署名、旧贡献保留已确定。
8. 账号删除/邮箱状态变化后的历史有效票政策；固定后的票据归档和审计保留。
9. 固定状态与映射JSON/API缓存间一致性、并发投票和夜间发布的原子边界。
10. 本人待审社区稿的可见性、编辑/撤回方式，沿用现有体验之外不擅加新规则。

## 13. 验收清单

- 固定 ID 改写解释后仍指同一意思；没有任何阅读器/巡检创建标准ID入口。
- 老词表、已有短语/帮助、原署名、收藏与进度不丢失。
- 已固定位置只返回一个标准义项并关闭投票；未固定位置返回全部合法候选。
- 至少5位有效用户、70%门槛按准确位置计算；跨位置不串票。
- 过期投票不计数并刷新固定解释，重试和并发不重复累计。
- 每位置最多一条公开社区解释，标准在前、社区在后，两者含义不冲突。
- 无署名旧稿显示旧版解释，有用户贡献继续显示From；替换后新作者署名、旧贡献保留。
- 有解释可收藏，无解释不收藏；不强制投票、不因改票或取消票直接改收藏。
- 同词条同sense学习状态归一，不同sense区分；原句精确关联、限量查询。
- 标准优先复习，社区作辅助；纯社区旧卡继续可用，可靠时才迁移。
- 缓存正常约1小时上限，故障暂用旧有效缓存，不弹手动更新要求。
- 分类、锚点、语义与权限检查分别可验证，不以UI模拟点击代替坐标校验。

## 14. 开发前置工作

本文只记录规则。下一阶段应先确定数据协议、精简标准资源形态、数据库/缓存、位置身份、迁移与接口，再编写实施计划和测试；不要根据历史问答中的已撤回选项建表。
