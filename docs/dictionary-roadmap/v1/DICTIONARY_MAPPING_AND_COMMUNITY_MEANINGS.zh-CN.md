# 词典映射、位置投票与用户补充释义：后续开发记录 v1

记录日期：2026-11-07
状态：需求与边界讨论记录，未实施，不是数据库迁移或生产发布授权。
词典源仓库：https://github.com/duwqijlk/english-wordnet

## 1. 目标

保留现有老词表和阅读支持，兼容后续基于 OEWN 固定义项 ID 的新书内映射。读者在任何单词位置都可以打开词卡：有确定解释时优先显示，没有时查询公共词典的全部候选义项。读者可针对**这本书的这个准确位置**给候选义项投票；夜间巡检逐步把可靠结果转成确定映射。

同时保留现有 **Write my own** 能力。标准释义不足以解释当前语境时，用户可以提供自己的解释；词卡可同时展示标准释义和明确标注的用户补充释义，两者不互相覆盖。

这里的“非标准”只表示**不是公共词典维护的标准解释**，不意味着一定错误。面向读者建议称为“用户补充 / Community explanation”，避免用标签贬低有效贡献。

## 2. 核心原则：义项身份不等于解释文字

- 一个固定的 `senseId` 代表一个固定意思。
- 同一个意思的学习释义可以改写得更简单、准确、自然，`senseId` 不变。
- 释义文字的修订号或资源构建号用于更新与缓存，不是另一个义项身份。
- 不能因为解释改了一句话，就强迫重新做所有书内映射或清空对应投票。
- 真正的义项合并、拆分、撤回或 ID 替代是特殊维护事件，需显式迁移记录，不能套用普通文字修订流程。
- 词典本体的变化与本站学习释义的变化应分别保留来源，不把改写后的学习释义误称 OEWN 原文。

示意：

```text
sense-123：固定表示某个意思
  学习释义修订 1：较难的英文解释
  学习释义修订 2：更简单的英文解释

意思没变 → sense-123 不变 → 书内映射仍有效
```

所有学习释义、语境补充及实际书籍阅读支持保持英文，采用简单、准确、自然的表达；中文只用于界面和管理文档。

## 3. 五类数据分别保存，不混成一份“意思”

| 数据 | 负责什么 | 不应该做什么 |
| --- | --- | --- |
| 公共词典义项 | 固定 ID、词形/词性、标准学习释义及修订 | 不存某本书位置的票数 |
| 书内确定映射 | 准确位置对应哪个 sense ID，含来源与修订 | 不复制后锁死公共解释，不由热度实时改写 |
| 旧词表解释 | 已经写好的释义、语境说明、短语与署名 | 不因新词典接入被覆盖或强制迁移 |
| 位置投票 | 这个位置对哪些标准义项有多少有效支持 | 不生成全词、全书或跨书通用排行榜 |
| 用户补充释义 | 某个准确位置的用户解释、作者与审核状态 | 不自动成为公共词典正文，不伪装标准释义 |

## 4. 新旧词表兼容

兼容粒度是**具体词条与位置**，不是规定一本书只能选旧模式或新模式。同一本书可以同时含旧解释、新映射，以及尚无解释的位置。

### 4.1 默认标准区的解析优先级

1. 当前位置有适用的旧词表专门解释：保留原解释及其原有署名。
2. 无上述解释，但有维护者确认的新映射：解析指定 `senseId` 的标准学习释义。
3. 无上述解释，但已有巡检正式发布的位置补充映射：解析该 ID。
4. 都没有：展示该单词的全部候选义项，并按**当前位置**的有效投票排序；没有票时用确定的词典默认顺序。
5. 未收录或资源不可用：明确提示，不冒充已经识别语境、不临时编造释义。

同一位置若同时存在旧解释和新映射，默认不静默覆盖旧解释。是否人工迁移该位置另行审核。

### 4.2 用户补充是并行层，而不是下一条回退

用户补充不应只在“标准释义没有结果”时才存在。标准区有内容时，仍可以显示适用的用户补充：

```text
所点单词

标准释义 / 现有书内解释
  原有解释，或准确映射的义项解释

用户补充
  针对本句的另一种英文说明
  贡献者、审核状态

Write my own
其他意思（按需展开）
```

- 两区同时展示的目标已提出；具体排版、默认展开几条尚未定稿。
- 老词表不应为了凑成双层结构又生成一份标准解释。保留其现有身份，不把用户原稿改标签后当作公共词典释义。
- 有用户补充时显示独立区；没有时不必放空白占位，也不应妨碍标准释义使用。
- 标准释义条目和用户补充必须在视觉、数据及 API 类型上明确区分。

## 5. 所有单词可点击，但不等于所有单词画线

- 已经标出的难词仍使用现有突出方式。
- 未标注普通词也可点击，进入公共词典候选查询。
- 需支持词形还原与匹配歧义，例如 `went → go`；遇到多个可能词条不能无说明强选一个。
- 短语优先等既有阅读行为应保留，不能因为“所有词可查”破坏短语和词卡操作。
- 不把每次普通点击都自动变成待新增词表的巡检任务；通用查询、缺失反馈和 Write my own 是不同事件。

## 6. API 能力：按义项解析与查全部义项分开

以下是接口职责，不是已确定的 URL 或最终 JSON Schema。

### 6.1 已知义项：精确解析

输入固定 `senseId` 以及对应词典资源/构建信息，返回该义项的学习释义、词性、来源和释义修订信息。支持批量 ID 查询，便于按书下载所需释义。

不必默认返回整个单词的所有意思。改写同一义项解释时，ID 保持，设备通过修订标识刷新。

### 6.2 未知义项：按词形查候选

输入所点词形及必要的语言/词条信息，返回匹配词条的全部候选义项。第一屏需要 ID、词性、学习释义，未必需要全部语义关系或所有例句。

“全部义项”指这个单词匹配到的词条义项，不是返回整部词典。候选数量很多时，可采用折叠或分页，但不能把接口截断结果误称完整候选。

### 6.3 位置上下文：票数与用户补充

以书籍/文本坐标版本/准确位置为输入，分别取得：

- 这个位置对各 `senseId` 的有效票数；
- 当前用户在这个位置的投票状态；
- 这个位置可公开展示的用户补充释义；
- 当前用户自己的待审核提交（若产品决定允许本人即时查看）。

前端可以调用一个聚合接口，但后端必须保持公共词典、位置数据和用户私有状态的边界。不得把某个位置的排行榜放进全局词典缓存。

### 6.4 Write my own

提交准确位置、原句上下文、所见词形、用户写的英文释义；可选关联某个 `senseId`，但不能强迫所有补充都绑定现有义项。提交者可能是在换一种方式解释既有义项，也可能是在指出词典尚未涵盖的用法。

关联必须区分“同一义项的语境补充”和“建议新增/修正义项”，不能用一段相似文字自动判为同一意思。

## 7. 投票的准确作用域

标准义项投票逻辑身份：

```text
书籍公共身份
+ 文本/坐标版本
+ 位置锚点
+ sense ID
```

用户去重逻辑身份再加 `userId`。不能仅凭单词拼写、章节、书名或相似原句合并。

```text
书 A · 位置 1 · bank
  金融机构义项：12 票
  河岸义项：2 票

书 A · 位置 3 · bank
  金融机构义项：1 票
  河岸义项：18 票
```

两个位置的排序各自独立，书 B 也不继承这些票。这里的“词典 ID 固定”与“位置票数隔离”是两个同时成立的规则。

### 7.1 锚点边界

- 使用公共书籍身份，例如 `catalog + id`，不能用每台设备的本地随机书籍 ID 当跨用户身份。
- 准确锚点应基于已定义的文本坐标体系；包含重复词出现位置，不能只记录 `bank` 或“第3章”。
- 不同 EPUB 版次若无法证明坐标对应，宁可暂不共享位置投票，也不能猜着合并。
- 文本坐标体系变化与学习释义改写分别处理；修改释义不应让位置身份失效。
- Unicode 码点、源文本、词形、偏移和绑定关系必须本地精确校验。语义正确与坐标正确分别检查，不能以模拟逐卡点击代替坐标验证。

### 7.2 用户补充的投票不是标准义项投票

若将来支持给用户补充点赞，目标应为独立 `contributionId`，并仍绑定当前位置。不能把补充的票自动算到关联 `senseId`，也不能反向共享标准义项的票数。

是否允许同一用户在一个位置给多个标准义项点赞、改票/取消规则、是否支持补充点赞尚未定稿。无论怎么定，都不能跨位置串票或重复点击累加。

## 8. 用户补充的展示、审核与署名

新增双层展示后，旧的“提交后审核并写进词表”不再足以表达全部状态。

建议区分：

| 状态/事件 | 含义 |
| --- | --- |
| 本人草稿/已提交 | 用户自己写的内容，尚不意味着对其他人公开 |
| 待审核 | 保留原稿和准确位置，等待审核 |
| 可公开展示的补充 | 审核通过后以用户补充身份展示，保留署名 |
| 修订/撤回/不展示 | 有明确原因与记录，不静默改成标准义项 |
| 被公共词典采纳 | 另一个独立事件，需核对是否仍为同一意思、修改许可及贡献记录 |

安全默认：他人的未审核原稿不立即公开；本人是否即时看到自己的提交需产品确认。用户补充按纯文本处理并限制长度，防注入、垃圾内容和误导。对是否公开及署名使用方式提供明确说明。

审核通过并公开补充，不等于已经改进公共词典；也不等于在老词表中采用了它。点赞、展示、设为位置映射、改写标准解释、贡献采纳是不同事件，不能共用一个“accepted”开关含混处理。

## 9. 夜间巡检：两条处理通道

### 9.1 标准义项位置映射

```text
无确定解释的位置
→ 用户对候选标准义项投票
→ 满足候选筛选条件
→ 巡检核对锚点、原句和该义项
→ 发布“此位置 → sense ID”
```

- 票数达到阈值只代表进入待复核集合，不凭最高票直接当真理。
- 统计不同用户的有效票，同时检查领先优势；10:1 和 10:9 不能同等处理。
- 具体票数、领先比例、最低样本量与防刷策略留待真实数据确定，不在文档中虚构一个已批准阈值。
- 默认只补没有确定解释/映射的位置，不以热度覆盖旧解释或维护者确认映射。
- 固定后不随实时排名来回切换；仍允许报告错误、修正与撤回，并记录发布依据。

### 9.2 用户补充释义

```text
Write my own 提交
→ 检查位置及英文内容
→ 审核为当前位置的补充解释
→ 与标准解释并列发布，保留用户署名
```

- 补充有用，不一定需要替换标准解释。
- 如果指出标准学习释义太难，可另外提出对公共义项解释的改写；不能把一次局部补充自动应用到所有书。
- 如果发现映射选错义项，修复的是位置映射，不是为了适配这句话篡改原义项含义。
- 真正缺失的义项进入词典维护流程，不用给错误的旧 ID 硬套新意思。

### 9.3 巡检工作流和文档同步

后续需在正式开发时更新 `docs/GLOSSARY_PATROL.md`，并检查 `docs/MAINTENANCE.md`、词典维护说明及贡献规则。当前不直接改现行巡检权限或 SQL。

保留现行安全原则：明确截止时间、按实际审核过的 ID 完成、分页与有界工作量、发布前快照、最新基线检查、发布后回读、贡献署名核验、失败不标记完成。

新增需要检查的边界：

- 巡检候选只扫描新增或变化的位置，不每晚全表扫描重算。
- 审核后新增票数、用户改票或文本版本变化，需检查所审核证据是否仍成立。
- 定义写在 Git、位置映射发布在站点数据层，两者不是一个跨系统事务；记录各自确切版本，分步验证，失败可定位。
- 旧报告 `resolved/fixed/already_covered/no_change` 不自动映射为用户补充的公开/采纳状态。
- 不因候选已展示就批量关闭历史反馈，不为新系统无证据重分配旧贡献。

## 10. 更新与缓存

建议分别管理以下标识，而不是每次改变都让所有书籍重新下载：

| 修订标识 | 发生变化的原因 |
| --- | --- |
| 标准释义修订 | 同一 sense ID 的解释文字优化 |
| 词典构建/源版本 | 派生资源重新构建或上游源更新 |
| 书内映射修订 | 某个位置增加、改选或撤回 sense ID |
| 位置排序修订 | 对该位置的有效票数发生变化 |
| 用户补充修订 | 补充文本、审核/展示或署名状态变化 |

- 标准义项及单词候选集合可按词典构建缓存复用；位置投票和补充缓存必须包含准确位置。
- `myVote`、本人待审内容等私有数据不能混进公共缓存。
- 不缓存一个词典查询失败为“永远没有这个词”。
- 已映射位置可在加书或更新时批量解析释义，阅读时本地使用。
- 任意单词回退查询需要单独考虑设备词典缓存或按需网络查询，不能只缓存已映射义项就宣称所有词离线可查。
- 离线时保持已有释义和用户本地已存数据；无缓存则诚实提示，不阻断阅读。
- 只下载标准释义更新，不应把书籍标成新上架、清空进度或重新占用书籍下载名额。
- 释义改写后位置票数继续跟随同一 ID，但用户补充可能引用旧文字；保留其创建时来源修订，必要时重新审核适用性，不擅改用户原文。

## 11. 数据部署与免费 D1 注意事项

当前建议而非已定部署架构：

- Git/YAML 是公共词典及分义项学习释义的维护源，SQLite 是派生产物。
- 完整 OEWN 关系图可保留在制作端，读者服务只需要必要的词条、词形、义项、解释与来源信息。
- 仓库原有 `scripts/wordnet_sql.py` 包含 Python pickle BLOB，不能原样作为 Workers 网页查询解释的接口；需生成适合 JS/SQL 读取的文本/结构化服务数据。
- 可以评估独立只读词典 D1、R2 版本化分块、设备本地词典等组合；不能先假定所有点击必须访问 D1。
- 位置投票与用户补充属于会增长的用户数据，应与只读词典发布分开设计。

2026-11-07 核对的免费限制：D1 每库500MB、账户合计5GB，每日500万行读取、10万行写入；索引增加存储和写入，导入/重建不能当作免费无限操作。Workers Free 每日10万请求也需要一并计算。额度与政策可能变化，实施前复核官方页面，不将这些数字当永久配置。

仅当用户投票、改票、提交补充时才需要相应写入，不为了每次展开词卡记录一条 D1 写入。统计每位置/用户投票量、提交量和必要索引的写放大，并测量实际派生库大小及查询 `rows_read/rows_written` 后再决定。

## 12. 当前代码事实与实现缺口

本次仅为讨论记录，未实现下述新接口或新数据表。

只读核对到当前阅读器：

- `src/lib/glossary-format.ts`：现有词表版本1/2，主要保留内嵌 `meaning`、语境、anchors、senses 等字段；尚非本方案的 OEWN 映射完整协议。
- `src/components/word-feedback.tsx`：已有 Write my own；目前作为反馈 suggestion 提交，按有无解释分别处理，不是完整的“标准 + 已审核用户补充”并列展示系统。
- `src/components/reader.tsx`：已有词位置上下文和适用性判断，但新投票身份不能不加验证就直接套用本地书籍 ID 或现有所有反馈字段。

现有反馈表、报告去重、贡献聚合、巡检 SQL、同步与导出需要逐项核对后升级；不能因为有 Write my own 按钮就宣称本方案已经兼容。

## 13. 建议开发顺序

1. 固定 ID/资源版本、位置坐标与新旧解释兼容协议，加入精确绑定测试。
2. 实现公共义项解析和全部候选查询，保留老词表行为及失败回退。
3. 实现位置映射补充层，使旧书无需重写整个词表即可增加绑定。
4. 实现位置投票和去重，不跨书、版本或位置传播。
5. 升级 Write my own 的存储、审核及双区展示，明确本人/他人可见性。
6. 更新夜间巡检工作文档和实现，先生成候选、人工可核验，再受限发布。
7. 根据真实规模优化批量解析、设备缓存和部署；不先加复杂推荐或统一全局词义排行榜。

每个后续方案/发布使用独立版本目录，旧记录保留，不原地抹掉来源、构建哈希和验证证据。本文为 `docs/dictionary-roadmap/v1/` 下的首次讨论记录。

## 14. 待定事项

- 新映射格式字段、schema版本与本地缓存/服务端协议。
- 公共词典精简SQLite的实际大小、行数、索引与部署方式。
- 用户补充默认展示几条、是否折叠、排序及审核后公开规则。
- 本人待审稿是否即时可见，如何修改、撤回与跨设备同步。
- 标准义项与用户补充各自的投票规则，是否允许一个位置多选。
- 巡检入队阈值、领先优势、反刷、证据失效与撤回策略。
- 老反馈迁移是否有足够位置与身份信息；无法证明的旧记录不能强行绑定。
- 采纳与署名、用户内容许可、隐私及删除请求对公共贡献记录的处理。

## 15. 验收边界

- 老词表原有解释、短语、生词、署名和阅读进度不变。
- 相同 sense ID 改写文字后仍解析同一个意思；映射和票数不因文字改写丢失。
- 同书不同 bank 位置的票数互不影响，不同书/无法对应的文本版本也隔离。
- 未标注位置展示全部候选，不假装已经确定当前义项。
- 位置确认映射后不随实时热度闪变，错误可报告、可撤回。
- 同一词卡可同时显示有来源的标准解释和明确标注的适用用户补充；用户原稿不会偷偷改成词典标准。
- 重复点击、取消、并发、离线重试和巡检重复运行不会多计票或重复授信。
- 精确源坐标、Unicode偏移、词形与sense绑定在本地校验；生成词典不逐卡模拟点击，实际UI改造另行用浏览器验证。
- 不把文档中的建议、阈值占位或未实施接口描述成现有功能。
